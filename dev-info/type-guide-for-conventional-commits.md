# Type Guide for Conventional Commits

> Generated by Microsoft Copilot on July 24, 2026

A structured, practical guide on when to use each type in a conventional commit message.

## The de‑facto standard commit types

Ten de‑facto standard commit type:<br>
`build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `style`, `test`

Two official are types: `feat`, `fix`

Eight types are added to the de‑facto standard commit type list from the Angular convention:<br>
`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `style`, `test`

## Version Bumps and Commit Types

Release types:
- `feat` — Triggers MINOR version bump
- `fix` — Triggers PATCH version bump
- `perf` — Triggers PATCH version bump

Non-release types: `build`, `chore`, `ci`, `docs`, `refactor`, `style`, `test`
 - No version impact.

Breaking Changes - Triggers a MAJOR version bump

## When to Use Each Conventional Commit Type

Below is a consolidated, practical guide based on the spec, Angular convention, and real-world usage patterns.

### `build` — Build system or external dependency changes

Webpack, Rollup, Babel, package.json dependency updates, build scripts.

**No version impact.**

### `chore` — Maintenance tasks

Dependency bumps, cleanup, renaming files, updating configs not related to build or CI.

**No version impact.**

### `ci` — Continuous integration changes

GitHub Actions, CircleCI, Jenkins, pipelines, workflows.

**No version impact.**

### `docs` — Documentation-only changes

Use for README updates, API docs, comments that explain behavior, etc.

**No version impact.**

### `feat` — A new user-facing feature

Use when you add functionality that users can interact with or rely on.

**Triggers MINOR version bump.**

### `fix` — A bug fix

Use when you correct incorrect behavior in the codebase.

**Triggers PATCH version bump.**

### `perf` — Performance improvements

Use when you make code faster or more efficient without changing behavior.

**Often treated as a patch-level change.**

### `refactor` — Code changes that do not alter behavior

Restructuring, renaming, reorganizing modules, simplifying logic without changing output.

**No version impact.**

### `style` — Formatting-only changes

Whitespace, semicolons, lint fixes that do not change logic.

**No version impact.**

### `test` — Adding or updating tests

Unit tests, integration tests, test fixtures, mocks.

**No version impact.**

## Breaking Changes ⚠️

Any type can include a breaking change by adding:
- `!` after type or scope
	- Example: `feat(api)!: remove deprecated v1 endpoints`
- A `BREAKING CHANGE:` footer

**Triggers a MAJOR version bump.**

## How to Decide Which Type to Use (Practical Rules)

Ask: Does this change affect users?
- Yes → `feat`, `fix`, or `perf`
- No → one of the non-release types (`docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`)

Ask: Does this change alter behavior?
- Yes → `feat`, `fix`, `perf`
- No → `style`, `refactor`, `test`

Ask: Is this change about tooling or infrastructure?
- Build system → `build`
- CI/CD → `ci`
- General maintenance → `chore`

Ask: Is this change purely documentation?
- Yes → `docs`
